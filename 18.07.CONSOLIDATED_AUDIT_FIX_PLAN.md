## Normalized Severity

Use these priorities instead of the report labels:

- **P0 - release/financial integrity:** captured money can be lost or
  misapplied, credentials can be exposed, or concurrent writes can corrupt
  billing/session state.
- **P1 - fix next:** material security, compliance, operational, or revenue
  correctness issue with a recovery path or limited trigger.
- **P2 - scheduled:** bounded performance, resilience, API fidelity, or
  user-facing correctness issue.
- **P3 - backlog:** cleanup, maintainability, defense-in-depth, or minor UX.
- **Feature project:** real product gap that cannot be fixed safely as a small
  bug patch.
- **No code fix:** refuted, intentional, already backstopped, or based on a
  false contract assumption.

## P0 - Fix First

### P0.1 Captured payment after session close

**Findings:** FULL C-1 and C-16; BASIC C7 and C9.

Two claim paths discard a successful provider result when the table session is
already closed. Non-Stripe abandonment can leave a live provider transaction,
and the emitted `payment:refundRequired` event has no staff-facing listener.

**Implementation:**

1. In both payment claim paths, persist the captured payment as `SUCCEEDED`,
   mark it as requiring refund/reconciliation, and return `needsRefund`.
2. Define provider-specific abandonment behavior. Do not treat a local
   `ABANDONED` state as provider cancellation.
3. Add a persistent dashboard reconciliation alert for
   `payment:refundRequired`.
4. Add an owner-visible reconciliation queue so a socket disconnect cannot
   hide the alert.

**Acceptance:** tests cover capture after OPEN, PAID, CLOSED, and concurrent
session close for Stripe and non-Stripe callback paths.

### P0.2 BORICA ambiguous/late payment recovery

**Findings:** BASIC C6; FULL H-1 and M-7.

`isPaymentClaimable` excludes `FAILED`, while BORICA can move an ambiguous
transaction through recovery after the local row was marked failed. BORICA
also lacks Stripe-style periodic reconciliation.

**Implementation:**

1. Model recoverable provider states explicitly instead of broadly making all
   FAILED payments claimable.
2. Add BORICA reconciliation using `queryTransactionStatus`, with TTL,
   idempotent transitions, per-record error isolation, and metrics.
3. Route late successful captures into the same claim-or-refund workflow as
   P0.1.

**Acceptance:** fixtures cover pending, failed-then-captured, expired,
transient provider failure, duplicate callback, and already-settled session.

### P0.3 POS/table-session order race

**Findings:** FULL C-8; BASIC C8.

The real issue is a plain session read inside the transaction rather than a
locking read. The customer/QR and POS paths need the same invariant.

**Implementation:**

1. Lock the OPEN table-session row with `SELECT ... FOR UPDATE` immediately
   before order insertion.
2. Make force-open/close and order creation use a consistent lock order.
3. Reject the losing transaction without creating order items.

**Acceptance:** real PostgreSQL concurrency tests, not mocked transaction
tests, prove that close/force-open/order races cannot orphan an order.

### P0.4 Payment credential key migration

**Findings:** FULL C-3 and C-4.

Provider secrets can fall back to a key derived from `JWT_SECRET`. A direct key
swap would make existing encrypted credentials undecryptable.

**Implementation:**

1. Deploy a compatibility release that can read v1, strict v2, and explicitly
   enabled legacy plaintext while continuing to write v1. Writing v2 in this
   first release would break old instances during a rolling deployment.
2. Configure a strict base64-encoded 32-byte primary key and preserve the exact
   legacy v1 key source explicitly.
3. After every running instance understands v2, switch new writes to v2.
4. Re-encrypt v1/plaintext values with a dry-run-first, batched,
   compare-and-swap migration so concurrent settings changes are not lost.
5. Bind v2 ciphertext to restaurant and credential purpose with AES-GCM AAD
   and HKDF domain separation.
6. Verify every non-null credential is valid v2 with an authoritative database
   scan, then remove plaintext/v1 support and the legacy key in a later release.

**Acceptance:** round-trip tests for new ciphertext, legacy decrypt and
reencrypt, wrong keys, malformed ciphertext, and mixed-key deployments.

### P0.5 Deployment gate for the repair migration

**Finding:** FULL H-44.

The repair migration may hold locks while updating a hot table. This is P0 only
if it has not yet run in production.

**Implementation:**

1. Check production migration status before editing anything.
2. Measure affected row count and lock duration on a production-sized copy.
3. If unapplied and material, split backfill from the schema migration or batch
   it with resumable progress.
4. If already applied successfully, close the finding with evidence.
