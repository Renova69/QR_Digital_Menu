 Thermal Kitchen Printer Integration — Implementation Plan

 Context

 User asked: how hard is thermal printer integration (1–10), how to customize template per restaurant, how to split cold/hot kitchen + dessert routing, and how to test without owning
  a TCP printer. KDS already exists in the codebase but most restaurants will pair it with (or replace it by) physical kitchen printers — paper tickets remain the operational
 standard in most venues.

 Goal: Owners can plug an 80mm ESC/POS thermal printer (network or USB) into their kitchen, configure routing rules (HOT / COLD / BAR / DESSERT), and have ticket lines auto-printed
 when an order is placed — with per-restaurant template customization and end-to-end testability on Windows dev machines without any printer hardware.

 Why now: Tickets are the missing operational primitive for V3 — multi-location, POS sync, and inventory all depend on stations being modeled in the schema. Adding routing now
 (without printer hardware deployed) gives the KDS the same station semantics for free.

 Per-restaurant template

 Stored as JSON on Restaurant.printerReceiptTemplate:

 type ReceiptTemplate = {
   headerText: string;        // "BELLA NAPOLI · Sofia"
   footerText: string;        // "Благодарим!"
   fontSize: 'small' | 'normal' | 'large';
   showLogo: boolean;         // bitmap logo at top (slow on cheap printers)
   showTableNumber: boolean;
   showOrderNumber: boolean;
   showItemNotes: boolean;
   showTimestamp: boolean;
 };

 Edited in Settings → Kitchen → Receipt Template with a live SVG preview rendered by receiptline (no printer needed). Defaults provided so brand-new restaurants get a sensible ticket
  on day one.

 ---
 Routing: HOT / COLD / BAR / DESSERT

 Routing key lives on MenuCategory.printerStationId (industry standard — Toast, Square, Lightspeed all do this). Per-item override would explode UI complexity; categories are the
 right granularity.

 Algorithm in printer.service.ts enqueueOrderTickets(orderId):

 1. Load order with items → category → station → printers
 2. Group order items by stationId (null station → expeditor default)
 3. For each group:
      a. Render receiptline DSL using restaurant's template + order data
      b. For each enabled printer in station: create PrinterJob(PENDING)
 4. Emit `printer:job` socket event to `printer_<restaurantId>` room
 5. Agent picks up, sends ESC/POS to TCP:9100, replies `printer:job-ack`
 6. On ACK: PrinterJob.status = PRINTED, printedAt set
 7. On NACK or timeout >30s: status = FAILED, retry queue (max 3)

 Dessert example: create station Pastry (type DESSERT), assign categories Cakes, Ice Cream. Optionally assign Pastry to the same physical printer as Hot Kitchen — many small
 restaurants share one printer across stations, ticket separator at top makes the line cook hand off the dessert slip.

 Expeditor printer: if a station has type EXPEDITOR, it receives the full order summary (all items, all stations) — used at the pass to coordinate plates.

 ---
 Testing without a printer

 Three independent layers, all dev-machine friendly:

 1. SVG preview in the browser

 receiptline (npm i receiptline) compiles a DSL string to SVG. The Settings template editor renders the SVG live as the owner toggles options. Reused for "Test print" button which
 shows the rendered ticket in a modal instead of (or alongside) hitting a real printer.

 2. Virtual TCP printer (CI + integration tests)

 node-thermal-printer writes raw ESC/POS bytes to a TCP socket. A tiny Node script in apps/backend/test/utils/virtual-printer.ts listens on localhost:9100, captures bytes to a
 buffer, and receiptio (npx receiptio --command "encoded_hex" -o png) renders it to PNG for visual regression. Jest spec asserts:
 - correct codepage selected (Cyrillic test string round-trips)
 - station routing (an order with hot + cold items produces 2 distinct jobs)
 - template fields applied (footer text appears in payload)

 3. Mock agent for end-to-end

 A Node script (apps/backend/test/utils/mock-agent.ts) connects to the local backend via socket.io with a test bearer token, ACKs every job immediately, exposes received jobs over an
  HTTP endpoint. Playwright/e2e tests assert that placing an order results in N expected jobs visible at the mock agent's endpoint.

 Hardware confidence path: once virtual + mock pass, buy one cheap Xprinter XP-T80A (~$80) for a final smoke test before shipping. Not required to merge.

> how would work print serice for tcp                                                                                                                                                  
● Flow

  Order placed → Backend (Fly.io) → socket.io push → Print Agent (on-prem) → TCP:9100 → Printer
                                         ▲                    │
                                         └──── ACK ───────────┘

  Backend never opens TCP. Agent does. Backend only talks socket.io to agent.

  Why agent (not direct TCP from Fly)

  - Printer sits on restaurant LAN (192.168.x.x). Not routable from internet.
  - Opening printer to public internet = security disaster (no auth on port 9100).
  - Agent reverses connection: dials out to Fly over WSS:443. Firewall-friendly.

  Agent hardware

  - Raspberry Pi 4 / Zero 2W (~$35) or any mini-PC owner already has.
  - Plug into same router as printer via Ethernet/Wi-Fi.
  - Runs Node daemon via Docker or systemd.

  Backend side (printer.service.ts)

  async enqueueOrderTickets(orderId: string) {
    const order = await this.prisma.order.findUnique({
      where: { id: orderId },
      include: { items: { include: { menuItem: { include: { category: { include: { printerStation: { include: { printers: true } } } } } } } } }
    });

    const byStation = groupBy(order.items, i => i.menuItem.category.printerStationId);

    for (const [stationId, items] of Object.entries(byStation)) {
      const station = items[0].menuItem.category.printerStation;
      const payload = renderReceipt(order, items, station, restaurant.printerReceiptTemplate);

      for (const printer of station.printers.filter(p => p.enabled)) {
        const job = await this.prisma.printerJob.create({
          data: { printerId: printer.id, orderId, payload, status: 'PENDING' }
        });
        this.gateway.pushJob(printer.restaurantId, job);
      }
    }
  }

  Gateway side (printer.gateway.ts)

  @WebSocketGateway({ namespace: 'printer', cors: { origin: process.env.FRONTEND_URL, credentials: true } })
  export class PrinterGateway {
    @WebSocketServer() server: Server;

    async handleConnection(socket: Socket) {
      const token = socket.handshake.auth.token;
      const hash = sha256(token);
      const agent = await this.prisma.printerAgent.findFirst({ where: { tokenHash: hash } });
      if (!agent) return socket.disconnect();
      socket.join(`printer_${agent.restaurantId}`);

  import { io } from 'socket.io-client';
  import { ThermalPrinter, PrinterTypes, CharacterSet } from 'node-thermal-printer';
  import Database from 'better-sqlite3';

  const db = new Database('queue.sqlite');
  db.exec('CREATE TABLE IF NOT EXISTS jobs (id TEXT PRIMARY KEY, payload TEXT, printerId TEXT, attempts INT DEFAULT 0)');

  const socket = io(process.env.BACKEND_URL!, {
    auth: { token: process.env.AGENT_TOKEN },
    transports: ['websocket'],
    reconnection: true,
  });

  const printers = new Map<string, ThermalPrinter>();

  function getPrinter(host: string, port: number) {
    const key = `${host}:${port}`;
    if (!printers.has(key)) {
      printers.set(key, new ThermalPrinter({
        type: PrinterTypes.EPSON,
        interface: `tcp://${host}:${port}`,
        characterSet: CharacterSet.WPC1251_CYRILLIC,
        removeSpecialCharacters: false,
        lineCharacter: '-',
        width: 48,
      }));
    }
    return printers.get(key)!;
  }

  socket.on('printer:job', async (job) => {
    db.prepare('INSERT OR IGNORE INTO jobs VALUES (?, ?, ?, 0)').run(job.id, JSON.stringify(job.payload), job.printerId);
    await drainQueue();
  });

  async function drainQueue() {
    const pending = db.prepare('SELECT * FROM jobs WHERE attempts < 3').all();
    for (const job of pending) {
      try {
        const printer = getPrinter(job.host, job.port);
        const isConnected = await printer.isPrinterConnected();
        if (!isConnected) throw new Error('Printer offline');

        renderToPrinter(printer, JSON.parse(job.payload));
        await printer.execute();

        db.prepare('DELETE FROM jobs WHERE id = ?').run(job.id);
        socket.emit('printer:job-ack', { jobId: job.id, success: true });
      } catch (err) {
        db.prepare('UPDATE jobs SET attempts = attempts + 1 WHERE id = ?').run(job.id);
        socket.emit('printer:job-ack', { jobId: job.id, success: false, error: String(err) });
      }
    }
  }

  setInterval(drainQueue, 10_000); // retry pending every 10s
  setInterval(() => socket.emit('printer:heartbeat'), 30_000);

● Five options. Ranked.

  1. PrintNode (cloud bridge — easiest, paid)

  - Restaurant installs PrintNode desktop client (Win/Mac/Linux). 5 min setup.
  - Client auto-discovers USB/network printers, dials PrintNode cloud.
  - Backend calls POST https://api.printnode.com/printjobs with base64 raw bytes or PDF.
  - Cost: ~$5/printer/month.
  - Pro: zero infra on your side. Cyrillic works.
  - Con: vendor lock-in, recurring cost, third-party sees ticket content.

  2. Cloud-native printer (Star CloudPRNT / Epson Connect)

  - Buy printer with HTTP polling built in (Star TSP143IIIU CloudPRNT ~$300, Epson TM-m30III).
  - Printer polls your endpoint every 3–5s: GET /api/v1/printer/poll/:deviceId.
  - Backend returns ESC/POS bytes when job ready.
  - Pro: no agent, no extra hardware, printer handles reconnects.
  - Con: pricier printers (~$300 vs $80), polling latency (avg 2s).

    };
  }

  @Get('printer/job/:token')
  async fetchJob(@Param('token') token: string, @Res() res: Response) {
    const bytes = await this.printerService.getJobBytes(token);
    res.type('application/vnd.star.starprnt').send(bytes);
  }

  3. Tailscale / WireGuard VPN

  - Install Tailscale on Fly machine + on a Pi at restaurant.
  - Pi acts as subnet router exposing 192.168.1.0/24 to Fly via VPN.
  - Backend opens TCP:9100 directly to printer's tailnet IP. No socket.io agent.
  - Pro: backend opens TCP itself, simplest code path. Free tier covers small fleet.
  - Con: still need Pi at restaurant (just runs Tailscale, no custom code). Tailscale on backend = ops complexity.

  4. Browser-driven (WebUSB / Web Bluetooth from dashboard tablet)

  - Kitchen tablet/laptop with Chrome runs KDS-style page.
  - Page subscribes to socket.io, receives job, calls navigator.usb or navigator.bluetooth to push ESC/POS bytes to plugged-in printer.
  - Pro: zero server-side networking, no agent install.
  - Con: Chrome only, needs page open + foreground, USB driver permission prompt, fragile across browser updates. Only works when tablet awake.

  5. Local HTTP printer service on a PC

  - Restaurant installs small Windows/Mac app (Electron or single .exe) on existing POS PC.
  - App opens local HTTP server on http://localhost:8000/print.
  - Dashboard browser tab POSTs job to localhost when order arrives (via socket.io listener in dashboard).
  - Pro: no Pi needed if restaurant already has POS PC. No public exposure.
  - Con: dashboard tab must stay open. Still custom binary to maintain (basically still an agent — just on a PC instead of Pi).

     Fix: @Controller({ path: 'subscription', version: '1' }) — or just @Controller('subscription') and let global prefix + versioning prepend /api/v1.

     2. Webhook CSRF-blocked in production

     main.ts:65–72 has hardcoded CSRF_EXEMPT list. New /api/v1/subscription/webhook not in list, not matched by isWebhook (which checks === '/api/v1/payments/webhook'). Stripe POSTs
     will get 403 in prod. Plan never updates main.ts CSRF logic.
     Fix: Add explicit webhook path skip alongside existing isWebhook check.

     3. Raw body missing for new webhook → signature verification fails

     main.ts:104 registers express.raw for /api/v1/payments/webhook only, then express.json for everything else. Subscription webhook will receive parsed JSON, Stripe signature check
     throws. Plan Task 4 Step 5 hand-waves "If no raw body middleware exists yet, add" — middleware exists, just not on this path.
     Fix: app.use('/api/v1/subscription/webhook', express.raw({ type: 'application/json', limit: '5mb' })) BEFORE the global express.json.

     4. checkout.session.completed handler reads wrong payload shape

     Plan Task 4 applySubscriptionFromEvent reads sub.items.data[0].price.id for both checkout.session.completed and customer.subscription.updated. Checkout Session object has
     subscription (id string), not items.data. Must stripe.subscriptions.retrieve(session.subscription) to get price. Runtime crash on first checkout.
     Fix: Branch by event type; retrieve subscription via API when handling checkout session.

     5. Guard ignores owners — every owner gets FREE tier

     Plan Task 3 Step 2 guard reads user.staffRestaurant only. Schema User.restaurantId → staffRestaurant is for STAFF (PIN-linked staff). Owners link via Restaurant.ownerId (relation
      OwnedRestaurants on User, line 26). Owner JWT → staffRestaurant null → tier defaults FREE → owner cannot use own paid features.
     Fix: Guard must resolve restaurant from user.restaurants[0] (owned) OR user.staffRestaurant. Mirror checkRestaurantAccess pattern already used in repo.

     6. Stripe API version invented

     Plan Task 4: apiVersion: '2026-04-22.dahlia'. No such version exists. Real recent versions: 2025-10-29.acacia, 2024-12-18.acacia, etc. TS will accept the literal but Stripe
     rejects. Pin to whichever version the existing StripeProvider already uses for Connect.
     Fix: Read existing apps/backend/src/payment/providers/stripe.provider.ts, reuse same apiVersion.

     7. customer.subscription.updated with cancel_at_period_end: true will flip tier to FREE early

     Plan handles only subscription.deleted for cancellation. But when customer hits "cancel" in Portal, Stripe fires subscription.updated with cancel_at_period_end: true and status
     still active. The plan's applySubscriptionFromEvent runs, tier stays the paid tier (price unchanged). OK so far — but later events may flip earlier than intended depending on
     flow.
     Real bug: when subscription immediately cancels (not at period end), deleted fires now. When cancel_at_period_end, customer keeps tier until period end, then deleted fires.
     Plan's handler treats deleted as instant FREE — correct for end-of-period, premature if you cancel-now via Portal. Read current_period_end and cancel_at_period_end to log/decide.
     Fix: At minimum, log both fields. Optional: store tierExpiresAt to render "downgrades on X" badge.

     8. Race-protection test is a fake

     Plan Task 4 Step 7 spec body: expect(service).toBeDefined(). Comment says "actual test verifies updateMany called with tierUpdatedAt OR clause" — but no assertion does so. Whole
     timestamp-gate raison d'être untested.
     Fix: Mock prisma, fire two events with different event.created, assert updateMany where includes tierUpdatedAt: { lt: eventTime } and second (older) call hits zero rows.

     Architectural gaps (defeat the gating)

     A. Public menu has no path to read tier — FREE-tier cart still works for direct API callers

     Task 8 hides UI button via useFeature('orders:receive'). useFeature reads RestaurantContext.activeRestaurant.tier. RestaurantContext only populates from authenticated GET
     /restaurants — public menu visitors are unauth. tier will be undefined → useFeature returns FREE features → cart hidden. Good for UI.
     But: POST /api/v1/orders (the public order create endpoint) has no @RequireFeature (Task 6 Step 1 explicitly defers: "the public endpoint uses a different guard or no guard").
     Anyone with restaurantId + tableId can POST and bypass tier. SaaS gating bypassable.
     Fix: Public order endpoint must look up restaurant.tier from the restaurantId in the body and reject when tier lacks ORDERS_RECEIVE. No guard needed — service-level check using
     FeatureService.hasFeature. Same pattern for POST /assistance (Call Waiter) and POST /payments/session/.../intent (Pay-at-Table).

     B. Lazy translation gate will brick FREE/STARTER public menus

     Translation has three call paths (CLAUDE.md): pre-warm, owner-triggered, lazy on-demand via GET /api/menu/public/:id?lang=<code>. Task 6 Step 4 puts
     @RequireFeature(LANGUAGES_MULTI) on translation controller with JwtAuthGuard — public menu has no JWT, so either guard blocks all public translation, or path is never hit. Need
     to gate at MenuService.findPublicMenu based on restaurant.tier, not via decorator.
     Fix: In public menu service, branch on tier before translating. FREE/STARTER → ignore lang param, return base content.

     C. Staff limit declared but never enforced

     getStaffLimit returns 1 | 5 | Infinity. Plan never wires into staff creation. Owners on FREE/STARTER will keep adding staff. Either remove method (YAGNI) or enforce in
     users.service.ts create path.
     Fix: In existing staff-create code, count current staff for restaurant, reject when ≥ getStaffLimit(restaurant.tier).
