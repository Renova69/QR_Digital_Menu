## 1. Why This Was Done

A comprehensive UI/UX audit identified 7 critical problems in the dashboard:

| # | Problem | Severity |
|---|---------|----------|
| 1 | `SettingsView.tsx` was a 1,172-line mega-component with 30+ `useState` hooks | 🔴 Critical |
| 2 | Dashboard had 11 navigation targets (8 tabs + 3 external links) | 🔴 Critical |
| 3 | Mobile bottom nav had 7 items (UX best practice: max 5) | 🟡 High |
| 4 | Two icon libraries installed (`@fortawesome` + `lucide-react`) — bundle bloat | 🟡 High |
| 5 | No reusable UI primitives — every component had its own inline styles | 🟡 High |
| 6 | Toggle switches used a fragile `sr-only` checkbox hack repeated 6+ times | 🟠 Medium |
| 7 | Status colors were hardcoded per-component, causing color drift | 🟠 Medium |

## 2. Phase 1 — Settings Decomposition

### What Changed

The monolithic `SettingsView.tsx` (1,172 lines) was split into **4 focused sub-components** under a new `settings/` directory. The original file was reduced to a ~260-line orchestration shell that:

- Holds shared state (all `useState` hooks for the form fields)
- Renders the 4-tab internal navigation (General / Loyalty / Payments / Staff)
- Handles the unified `handleSave()` API call
- Renders the `BrandingEditor` below the tab panel

### New Directory Structure

```
pages/Dashboard/
├── SettingsView.tsx              ← Thin shell (~260 lines, was 1,172)
├── settings/
│   ├── index.ts                  ← Barrel export
│   ├── GeneralSettingsTab.tsx    ← Location, Contact, Timezone, Localization
│   ├── LoyaltySettingsTab.tsx    ← Loyalty toggle, Points economy, VIP tiers, Happy Hour
│   ├── PaymentSettingsTab.tsx    ← Stripe Connect, Tips configuration
│   └── StaffSettingsTab.tsx      ← Staff CRUD, Device bonding, Shared device mode
```

### What Each Sub-Component Owns

#### `GeneralSettingsTab.tsx` (~170 lines)
- Address & Contact info inputs
- Timezone selector (moved `TIMEZONES` constant here since only this tab uses it)
- Language selection chips (moved `AVAILABLE_LANGUAGES` constant here)
- "Translate All Now" force-translation action

#### `LoyaltySettingsTab.tsx` (~280 lines)
- Loyalty program enable/disable toggle
- Points economy: signup bonus, earn rate, redeem rate
- Live cashback preview with warning when rate is too high
- Point expiry configuration
- VIP tier thresholds and multipliers (Silver / Gold)
- Happy Hour gamification settings
- Payment notification toggle
- **Icon migration done inline:** `faTriangleExclamation` → `AlertTriangle`, `faMedal` → `Award`

#### `PaymentSettingsTab.tsx` (~170 lines)
- Payments enable/disable toggle with Stripe warning
- Stripe Connect button / disconnect flow
- Tips configuration (enable toggle + quick-tip % buttons)
- **Local state:** `stripeLoading` and `newTipOption` moved here (were polluting parent)

#### `StaffSettingsTab.tsx` (~280 lines)
- **Fully self-contained** — all staff-related state was moved out of the parent:
  - `staffMembers`, `staffLoading`, `staffError`
  - `inviteName`, `inviteEmail`, `inviteRole`
  - `sharedDeviceConfig`, `sharedDeviceMessage`
  - `deviceEnrollmentUrl`, `deviceEnrollmentExpiresAt`, `deviceEnrollmentLoading`
  - `staffCreatedModal` object
- Shared Device Mode (enable/disable, bond a device)
- Staff invite form (name, email, role)
- Staff table with role badges
- Device QR generation and copy-link functionality
- Renders `StaffCreatedModal` directly
- **Icon migration done inline:** `faQrcode` → `QrCode`, `faTrash` → `Trash2`, `faCopy` → `Copy`, `faCheck` → `Check`

### How `SettingsView.tsx` Works Now

```
SettingsView (shell)
├── Tab bar: General | Loyalty | Payments | Staff
├── <form onSubmit={handleSave}>
│   ├── activeTab === 'general'  → <GeneralSettingsTab ... />
│   ├── activeTab === 'loyalty'  → <LoyaltySettingsTab ... />
│   ├── activeTab === 'payments' → <PaymentSettingsTab ... />
│   └── activeTab === 'staff'    → <StaffSettingsTab ... />
│   └── Save button (hidden for payments/staff — they have their own)
└── <BrandingEditor ... />
```

## 3. Phase 2 — Navigation Consolidation

### What Changed

The dashboard went from **11 navigation targets** down to **4 primary tabs**. Secondary views are nested as sub-tabs within their parent.

### Before vs After

| Before (11 targets) | After (4 primary tabs) |
|---------------------|----------------------|
| Summary | **Home** → Summary + Quick Actions |
| Orders | **Operations** → Orders sub-tab |
| Assistance | **Operations** → Assistance sub-tab |
| Tables & QR | **Operations** → Tables sub-tab |
| Analytics | **Analytics** → Analytics sub-tab |
| Payments | **Analytics** → Payments sub-tab |
| Settings | **Settings** → Settings sub-tab |
| Import | **Settings** → Import sub-tab |
| Menu Editor (link) | **Home** → Quick Actions link |
| POS (link) | **Home** → Quick Actions link |
| Kitchen (link) | **Home** → Quick Actions link |

### Mobile Bottom Navigation

| Before | After |
|--------|-------|
| 7 items (violated 5-item UX rule) | **4 items**: Home, Operations, Analytics, Settings |

### New File: `OperationsView.tsx`

A new container component that groups Orders, Assistance, and Tables under a single "Operations" tab with its own sub-tab navigation:

```
OperationsView
├── Sub-tab bar: Orders | Assistance | Tables
│   (with badge counts for new orders + unresolved requests)
├── activeSubTab === 'orders'     → <OrdersView />
├── activeSubTab === 'assistance' → <AssistanceView />
└── activeSubTab === 'tables'     → <TableView />
```

### Legacy URL Compatibility

Old bookmark URLs like `?tab=orders` or `?tab=assistance` still work. A `LEGACY_TAB_MAP` in `DashboardPage.tsx` maps them to the new structure:

```typescript
const LEGACY_TAB_MAP: Record<string, TabId> = {
  summary: 'home',
  orders: 'operations',
  assistance: 'operations',
  tables: 'operations',
  analytics: 'analytics',
  payments: 'analytics',
  settings: 'settings',
  import: 'settings',
};
```

### `DashboardPage.tsx` Changes

The file was fully rewritten to support the new 4-tab architecture:

- **Desktop:** Horizontal pill-style tab bar with 4 tabs (was 8+)
- **Mobile:** Fixed bottom nav bar with 4 items + active indicator bar
- **Sub-views:** Analytics has optional Payments sub-tab (only when `paymentsEnabled`); Settings has optional Import sub-tab
- **Quick Actions:** POS, Kitchen, and Menu Editor links moved to the Home tab as secondary action buttons
- **ARIA:** All tab buttons now have `role="tab"` and `aria-selected` attributes
- **Badge counts:** Operations tab shows combined count of new orders + unresolved requests

## 5. Phase 4 — Reusable UI Primitives

Four new reusable components were created in `components/ui/`. These are **ready for adoption** but have not yet been wired into existing components — they are designed as drop-in replacements that can be adopted incrementally.

### `GlassCard.tsx`

**Purpose:** Base glass-morphism surface replacing the repeated `glass-panel` + `border-white/5` + `rounded-[2.5rem]` pattern used 20+ times across the dashboard.

```tsx
<GlassCard className="p-8" radius="2rem" onClick={handleClick}>
  {children}
</GlassCard>
```

**Features:**
- Configurable border-radius (defaults to `2.5rem`)
- Optional click handler with cursor-pointer, hover shadow, and scale effect
- Keyboard accessible (`Enter`/`Space` triggers click, `tabIndex` set automatically)
- ARIA `role="button"` when interactive

---

### `StatCard.tsx`

**Purpose:** Dashboard stat card extracted from `SummaryView`'s repeated 3-card pattern (Revenue / Orders / Assistance).

```tsx
<StatCard
  label="Total Revenue"
  value={`€${revenue.toFixed(2)}`}
  Icon={TrendingUp}
  color="accent"
/>
```

**Features:**
- Accepts any `lucide-react` icon
- Configurable accent color (Tailwind color string)
- Animated accent bar that expands on hover
- Optional subtitle text below the value
- Built on top of `GlassCard`

---

### `StatusBadge.tsx`

**Purpose:** Centralized status → color mapping that prevents per-component color drift. Covers **all status types** in the app:

```tsx
<StatusBadge status="NEW" dot />
<StatusBadge status="OWNER" label="Owner" />
<StatusBadge status="succeeded" size="md" />
```

**Centralized `STATUS_COLORS` map covers:**

| Domain | Statuses |
|--------|----------|
| Orders | `NEW`, `IN_PROGRESS`, `SERVED`, `COMPLETED`, `CANCELED` |
| Staff roles | `OWNER`, `MANAGER`, `WAITER`, `KITCHEN` |
| Payments | `succeeded`, `pending`, `failed`, `refunded` |
| Tables | `occupied`, `waiting`, `paid`, `empty`, `free` |

**Features:**
- Optional pulsing dot indicator (animated for `NEW` and `IN_PROGRESS`)
- Two sizes: `sm` (default) and `md`
- Exported `STATUS_COLORS` map for direct use when the badge component doesn't fit

---

### `Toggle.tsx`

**Purpose:** Standardized toggle switch replacing the fragile `sr-only` checkbox + styled `<div>` hack that was copy-pasted 6+ times across Settings tabs.

```tsx
<Toggle
  checked={isEnabled}
  onChange={setIsEnabled}
  label="Enable Loyalty"
  showLabel
/>
```

**Features:**
- Proper ARIA `role="switch"` with `aria-checked`
- Keyboard accessible (click via `Enter`/`Space`)
- `focus-visible` ring for keyboard navigation
- Two sizes: `sm` and `md`
- Disabled state with reduced opacity
- Auto-generated unique IDs via `useId()`
