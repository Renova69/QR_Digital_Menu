## CRITICAL (14 findings)

### C1 — Kitchen order-status update silently fails

**Agent:** silent-failure-hunter | **File:** `apps/frontend/src/pages/staff/KitchenPage.tsx:170`

`catch {}` around `updateOrderStatus(orderId, next[current])`. If the API call fails (network error, 500, timeout), kitchen staff sees no error, no toast. They believe the order status changed. Food prep continues based on stale status. A "NEW" order the kitchen thinks they moved to "PREPARING" may never start cooking.

**Fix:** Remove empty `catch {}`. Show error toast. Let error propagate so caller can revert UI state.

### C2 — GDPR retention cron has no error handling

**Agent:** silent-failure-hunter | **File:** `apps/backend/src/users-data/retention.service.ts:20-72`

`runDailyRetention()` runs three sequential Prisma operations (delete expired verification tokens, anonymize old orders, prune menu views). None wrapped in try/catch. If first `deleteMany` throws (connection pool exhaustion, transient DB error), order-anonymization and menu-view pruning never run. GDPR violation — old orders retain customer PII indefinitely.

### C3 — Reservation reminder sweep aborts mid-batch on first failure

**Agent:** silent-failure-hunter | **File:** `apps/backend/src/reservations/reservation-reminder.service.ts:30-108`

Cron `runReminderSweep()` calls `sweep()` which loops over reservations and `await`s `this.notifications.notify(...)` for each. `sweep` itself has **no try/catch** around the loop. Any DB error (updateMany at line 76, findMany at line 41) aborts entire sweep mid-batch. Up to 199 remaining reservations won't receive reminders. Increases no-show rate.

### C4 — WebSocket evictUser/evictDeviceToken catch no errors (auth enforcement bypass)

**Agent:** silent-failure-hunter | **File:** `apps/backend/src/events/events.gateway.ts:809-835`

`evictUser()` and `evictDeviceToken()` iterate over all connected sockets. If `this.server.fetchSockets()` throws or a single socket `.emit()` throws, error propagates unhandled. ### C6 — isPaymentClaimable rejects FAILED status — Borica TRTYPE=90 recovery permanently loses captured money

**Agent:** payment-provider-reviewer | **File:** `apps/backend/src/payment/core/payment-core.service.ts:936`

Stale-pending Borica recovery path in `borica-checkout.service.ts` (lines 212-293) calls `markBoricaStatusUnknown` then marks payment FAILED when TRTYPE=90 returns inconclusive. If Borica transaction actually succeeded, payment is FAILED. ### C7 — abandonCheckout marks ePay/MyPOS/Borica PENDING payments ABANDONED without cancelling at provider

**Agent:** payment-provider-reviewer | **File:** `apps/backend/src/payment/session/payment-session.service.ts:372`

Lines 376-378: non-Stripe payments (ePay, MyPOS, Borica) unconditionally added to `abandonedIds` without contacting provider. Stripe payments get `stripe.cancelPaymentIntent()` — genuinely cancels the intent. For ePay/MyPOS/Borica, `abandonCheckout` marks them ABANDONED in DB but transaction still live at provider. Waiter can then close session (force-close or card/cash close). When provider notification arrives, `claimSuccessfulPaymentForOpenSession` finds session no longer OPEN (it's CLOSED_NO_PAYMENT or PAID) and returns `{ claimed: false, sessionPaid: false }`. Money captured at provider but ABANDONED in our books permanently.

**Fix:** `abandonCheckout` must either leave non-Stripe payments PENDING so `abandonCheckoutOrThrowIfPending` blocks close, or add clock/expiry mechanism, or claim path for non-Stripe providers should re-open CLOSED_NO_PAYMENT session.

### C8 — Force-open concurrent-order race orphans items on closed session

**Agent:** pos-session-auditor | **File:** `apps/backend/src/payment/session/payment-session.service.ts:629-707` + `apps/backend/src/orders/orders.service.ts:839-917`

Force-open locks `table_session` row (FOR UPDATE). Order creation locks `restaurant_table` row (FOR UPDATE). Different rows = no serialization. Race sequence:

1. Force-open: abandon pending (outside tx)
2. Order-create: lock TABLE row
3. Order-create: find OPEN session (still OPEN)
4. Order-create: create order with session S, commit
5. Force-open: lock SESSION row
6. Force-open: close session S → CLOSED_NO_PAYMENT, create new session

Order at step 4 now attached to session S which is CLOSED_NO_PAYMENT. Invisible to POS workflow — `getSessionBill` only finds OPEN sessions, `getTableOrders` only searches OPEN/PAID. Waiter sees empty new session, must re-enter items.

**Fix:** `forceOpenSession` should also acquire `FOR UPDATE` on table row inside its transaction, or order creation should lock session row instead of table row.
