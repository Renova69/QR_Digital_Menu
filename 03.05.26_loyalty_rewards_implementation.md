# May 2026 - Major Loyalty System Rewrite

## Overview

In May 2026, the loyalty system underwent a complete rewrite to address critical issues with the original implementation and to add professional-grade point tracking with expiry handling.

### Problems Fixed

1. **Simple Point Balance** - Original system used a single `points` number with no expiry tracking
2. **Hardcoded Values** - Logic ignored dashboard settings
3. **Multiplier Stacking** - Additive formula silently discarded tier bonuses

Created a new model for FIFO point tracking:

```prisma
model LoyaltyPointLedger {
  id                String   @id @default(cuid())
  loyaltyAccountId   String
  loyaltyAccount    LoyaltyAccount @relation(...)

  order            Order?    @relation(...)

}
```

### Transaction Types Enum

```prisma
enum LoyaltyPointTransactionType {

  SIGNUP     // Signup bonus

  ADJUSTMENT // Admin adjustments
  EXPIRE    // Points that expired
  REFUND    // Points refunded
```

## 2. New Backend Utilities

### `apps/backend/src/loyalty/loyalty-ledger.utils.ts`

Created new utilities for professional point management:

#### `addDays(date, days)`

Adds days to a date - used for expiry calculation.

#### `getRewardValue(points, redeemRate)`

Calculates ��� value: `points / redeemRate`.

#### `getFirstRewardProgress(points, redeemRate)`

Returns progress to first reward:

- `percent`: Progress percentage
- `pointsToReward`: Points until next reward
- `rewardThreshold`: Points needed for €1

#### `expireAccountPoints(tx, loyaltyAccountId)`

- Finds all point batches with `expiresAt <= now`
- Sets `remainingPoints = 0` on expired batches
- Creates EXPIRE transaction record
- Decrements loyalty account balance
- Prevents negative balance

#### `redeAccountPoints(tx, loyaltyAccountId, pointsToRedeem, orderId)`

- FIFO redemption (oldest points first)
- Updates each batch's `remainingPoints`
- Creates REDEEM transaction record
- Throws if ledger doesn't match balance

#### `addEarnedPointBatch(tx, loyaltyAccountId, points, type, expiresAt, orderId)`

- Creates new ledger entry for earned points
- Sets expiry date from config
- Separate tracking for EARN vs SIGNUP

#### `getExpiringPointBatches(tx, loyaltyAccountId, reminderDays, now)`

- Returns batches expiring within reminder window
- Used for push notification triggers

# May 3, 2026 — Loyalty Audit, Bug Fixes & Professional Enhancements

## Overview

Following a full code audit of the May 2026 rewrite, five real bugs were identified and fixed. Four new features/improvements were added to bring the system to production quality: timezone-aware happy hour, fully configurable VIP tiers (per restaurant), a working automated expiry reminder system (cron + manual endpoint), and DTO input validation guards.

All TypeScript compilations (`npx tsc --noEmit`) pass with zero errors on both frontend and backend.

---

## Bugs Found and Fixed

### Bug 1 — Happy Hour Ignored Timezone

**File:** `apps/backend/src/orders/orders.service.ts`

**Problem:** `new Date()` returns UTC. If the restaurant is in UTC+3 and happy hour is `18:00–20:00`, the UTC time could be 15:00–17:00 — a 3-hour offset that silently mis-triggers or misses happy hour entirely.

**Fix:** Used **Luxon** (already installed) with the restaurant's IANA `timezone` DB field:

```typescript
import { DateTime } from 'luxon';

const tz = restaurant.timezone || 'UTC';
const nowInTz = DateTime.now().setZone(tz);
const currentMinutes = nowInTz.hour * 60 + nowInTz.minute;
```

The `timezone` field was already in the schema (`String? @default("UTC")`) — just unused.

---

### Bug 2 — VIP Tiers Were Hardcoded (Ignored Dashboard Settings)

**File:** `apps/backend/src/orders/orders.service.ts` (and `loyalty.service.ts`, `CustomerProfilePage.tsx`)

**Problem:** Thresholds of 500 (Silver) and 2000 (Gold) were hardcoded in three different places. The dashboard Silver/Gold threshold settings did nothing. Tier multipliers were also hardcoded at 1.2/1.5 instead of reading from the DB.

**Fix:**
1. Added 4 new fields to the `Restaurant` schema (see schema section below).
2. Created `loyalty-tiers.utils.ts` as single source of truth for tier calculation.
3. Updated `orders.service.ts` and `loyalty.service.ts` to use the utility.
4. Frontend (`CustomerProfilePage.tsx`, `CheckoutPage.tsx`) now reads tier info directly from API response.

---

### Bug 3 — Free Item Redemption Still Charged Options

**File:** `apps/backend/src/orders/orders.service.ts`

**Problem:** When a customer redeemed a free item (via `redeemItemIds`), the base price was correctly zeroed but option add-ons (e.g. "extra sauce +€0.50") were still added to the bill, so a "free" item could still cost money.

**Fix:** Introduced `isRedeemedFree` guard — when an item is a free redemption, its options are also zeroed:

```typescript
const isRedeemedFree =
  createOrderDto.redeemItemIds?.includes(item.menuItemId) && dbItem.rewardPointsPrice;

if (isRedeemedFree) {
  itemsPointsRedeemed += dbItem.rewardPointsPrice;
  itemPrice = 0;
}
let optionsTotal = 0;
if (!isRedeemedFree && item.selectedOptions?.length) {
  // charge options normally only for non-free items
}
```

---

### Bug 4 — `reminderSentAt` Was Never Written (Reminder System Inoperative)

**File:** `apps/backend/src/loyalty/loyalty.service.ts` and `loyalty-ledger.utils.ts`

**Problem:** The `reminderSentAt` field existed on `LoyaltyPointLedger` and `getExpiringPointBatches` already filtered by it, but nothing ever wrote to it. The GET endpoint returned candidates but calling it again would return the same candidates again — reminders could be "sent" infinitely.

**Fix:**
1. Added `markRemindersSent(tx, batchIds, now)` function to `loyalty-ledger.utils.ts`.
2. Added `onlyUnnotified = false` parameter to `getExpiringPointBatches` so we can filter `reminderSentAt: null`.
3. Split the reminder logic into two endpoints:
   - `GET /:restaurantId/expiry-reminders` — read-only preview (does NOT mark as sent)
   - `POST /:restaurantId/expiry-reminders/notify` — marks batches as sent, returns count
4. Added a daily cron job at midnight that calls `notifyExpiryReminders` for all restaurants (see below).

---

### Bug 5 — `Promise.all` Inside Prisma Transaction (Potential Deadlock)

**File:** `apps/backend/src/loyalty/loyalty-ledger.utils.ts` — `expireAccountPoints`

**Problem:** Inside a `$transaction` callback, `Promise.all([...updateMany, ...updateMany])` was used to update expired batches. Running concurrent writes inside a serializable transaction is undefined behavior — Prisma/Postgres may deadlock or serialize them anyway at a cost, depending on isolation level.

**Fix:** Replaced with a single `updateMany` call that updates all expired batches in one statement:

```typescript
// Before (risky):
await Promise.all(expiredBatches.map(b => tx.loyaltyPointLedger.update(...)));

// After (safe):
await tx.loyaltyPointLedger.updateMany({
  where: { id: { in: expiredIds } },
  data: { remainingPoints: 0 },
});
```

### 2. Automated Expiry Reminder System (Cron + Manual Endpoint)

#### `apps/backend/src/loyalty/loyalty.service.ts`

**New method: `notifyExpiryReminders(restaurantId)`**
- Finds all loyalty accounts for the restaurant
- For each, finds unnotified batches expiring within `loyaltyExpiryReminderDays`
- Marks them as notified via `markRemindersSent()`
- Returns count of accounts notified
- Has a `// TODO:` placeholder to plug in real email/push service

**New cron job:**
```typescript
@Cron(CronExpression.EVERY_DAY_AT_MIDNIGHT)
async runDailyExpiryReminders() {
  const restaurants = await this.prisma.restaurant.findMany({
    where: { isLoyaltyEnabled: true },
    select: { id: true },
  });
  for (const r of restaurants) {
    await this.notifyExpiryReminders(r.id);
  }
}
```

Runs at midnight UTC daily. Works for all loyalty-enabled restaurants without manual triggers.

## Architecture: Single Source of Truth

The key architectural principle for tier logic:

```
Backend (loyalty-tiers.utils.ts)
  ├── getTierInfo(lifetimePoints, config) → TierInfo
  └── tierConfigFromRestaurant(restaurant) → TierConfig
         ↓
  orders.service.ts → uses for multiplier during order
  loyalty.service.ts → uses for buildRewardSummary response
         ↓
  API Response includes: { tier, tierMultiplier, tierProgressPercent,
                           pointsToNextTier, nextTierName }
         ↓
  Frontend (CustomerProfilePage, CheckoutPage)
    → reads from API, no tier logic on client
```
