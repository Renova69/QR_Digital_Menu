## 🔴 Confirmed CRITICAL — fix these first

### C-1: Payment stuck PENDING forever after session closes before Stripe confirms

**File:** `apps/backend/src/payment/core/payment-core.service.ts` — `claimSuccessfulPaymentForOpenSession` (~1029-1052), **and** the same bug independently in `claimSuccessfulScopedCheckoutPayment` (~1111-1125) — the report only found the first instance.
**Fix:** Both branches currently return `{claimed:false}` and silently give up when the session isn't OPEN anymore. Copy the pattern already used elsewhere in the same file for the analogous "money captured but shouldn't apply" case: set `providerStatus: 'SESSION_CLOSED_NEEDS_REFUND'`, mark the payment SUCCEEDED, return `{claimed:true, needsRefund:true}`. `emitPaymentClaimEvents` already handles `needsRefund` → emits `payment:refundRequired` (see C-16 below — needs a frontend listener to be useful).

### C-2: MyPOS card-terminal payments have zero provider confirmation

**Files:** `apps/backend/src/payment/session/payment-session.service.ts:522-583` (`closeSessionWithProvider`) **and** `payment-settlement.service.ts:421-596` (`settlePartial`, MyPOS branch — report missed this second site).
**Reality check:** this is not a quick patch. MyPOS does publish a real terminal-integration API (Cash Register Remote API / ePOS API) that could close this gap, but this codebase implements _only_ the hosted-checkout/redirect flow — zero terminal-pairing code exists to hook into. A correct fix means building new infrastructure: device pairing, a remote-charge API client, async terminal-response handling in the POS UI. **Treat as a feature project, not a bug-fix task.** Interim mitigation: relabel as "Card (unverified)" in UI/audit trail so it's not silently indistinguishable from a real confirmation.

### C-3: Payment secrets encrypted under JWT_SECRET fallback

**File:** `apps/backend/src/payment/secret-crypto.ts:6-20`.
**⚠️ Do not ship the naive fix.** Swapping to a dedicated `PAYMENT_SECRET_ENCRYPTION_KEY` and removing the JWT_SECRET fallback, without more, **will brick every restaurant's already-configured BORICA/ePay/MyPOS credentials** — `decryptSecret()` will hard-fail GCM tag verification against the old key, throwing on every payment attempt for every restaurant that has payment providers configured today.
**Correct fix (two-phase):**

1. Add dual-key decrypt support: try the new dedicated key, fall back to the legacy JWT_SECRET-derived key, and **re-encrypt under the new key on next write** (touch `restaurants.service.ts`'s update path).
2. Once telemetry shows the legacy fallback path is no longer hit (all secrets re-encrypted), remove the fallback.
3. Rename the ePay-specific error message/`PREFIX` to reflect all three providers (folds in LG-49).

### C-4: Unsalted single-round SHA256 key derivation

**File:** `apps/backend/src/payment/secret-crypto.ts:19`.
**Fix:** Lower priority than it sounds — see the domain-separation reasoning below. Once C-3 lands (dedicated, single-purpose key), this becomes optional hardening. If prioritized: switch to HKDF-SHA256 with an `info` label (e.g. `"payment-secret-encryption-v1"`) for domain separation. Do this as part of the same C-3 PR, not separately.

### C-5: Payment tolerance `0.01` hardcoded — worse than reported

**Files:** 16 call sites across 7 files (report only found 4-5): `payment-core.service.ts` (6 sites: 596, 842, 912, 997, 1101, 1229), `borica-checkout.service.ts:250,558`, `mypos-checkout.service.ts:335`, `payment-reporting.service.ts:480`, `payment-session.service.ts:99,106`, `payment-settlement.service.ts:318,578`.
**Fix:** Export `PAYMENT_TOLERANCE_EUR = 0.01` from a shared DI-free module (`payment-money.utils.ts`), import at all 16 sites.

### C-10: Zero `React.memo` in the frontend

**Confirmed**, but the report's "no `useCallback` either" claim is false — 19 files already use `useCallback`, it's just not paired with `React.memo` on the consuming components, so it currently buys nothing. **Fix priority order:** start with the pages driven by short-interval effects — `KitchenPage` (1s interval), `OrdersView` (10s interval) — and their child list-item components, since those are where continuous re-render actually costs something today. Don't blanket-wrap 30 files; target the interval-driven ones first.

### C-11: Only 2 ErrorBoundary instances

**Confirmed, with nuance:** the dashboard's own tab content already has a nested boundary (`DashboardPage.tsx:665`) — a crash inside a dashboard tab only blanks that tab, not the whole app. **Highest real risk is unprotected:** `PublicMenuPage`/`CheckoutPage` (customer-facing, zero fallback) and `PosPage`/`KitchenPage` (staff-facing, revenue-critical, zero fallback). Prioritize wrapping those two route groups first; SuperAdmin/OnboardingPage are lower priority (internal, lower traffic).

### C-16: `payment:refundRequired` emitted, zero frontend listeners

**File:** `apps/backend/src/payment/core/payment-core.service.ts:1391` (emit confirmed real, zero frontend `socket.on` anywhere).
**Fix:** Add a listener in the dashboard payments view alongside the existing `payment:confirmed` handler, surfacing a persistent alert with `paymentId`/`tableSessionId`/`amount` for staff reconciliation. This becomes actionable once C-1's fix starts actually emitting it for real cases.

### C-12 / C-13: i18n coverage — confirmed, worse for JA/RU/AR than for DE/FR/IT/ES/ZH

- **JA/RU/AR: ~19% key coverage, ~16% actually translated.** Not "only auto._ exists" as claimed — auto._ itself is only 13% translated; the deficit is spread across every namespace.
- **DE/FR/IT/ES/ZH: exactly the same 100 keys missing in all five** — precisely the newest feature additions (reservations, cash-assistance, upsell contexts, analytics payment-methods). ~92% baseline coverage otherwise.
  **Fix:** No existing tooling bulk-translates the UI-chrome locale files (DeepL integration in this repo is menu-content-only). Needs a new script wrapping DeepL for the 12 `translation.json` files. One run would close the DE/FR/IT/ES/ZH gap entirely (100 keys × 5 locales); JA/RU/AR need a much larger regeneration (~2600 keys × 3 locales) — budget this as a separate, bigger pass.

## 🟠 Confirmed HIGH

### Payments / Money

- **H-1 (BORICA non-final status throws, no reconciliation):** confirmed, and worse than reported — **no cron reconciliation exists for BORICA at all**, unlike Stripe's `reconcilePendingPayments`. A BORICA payment in persistent non-final status has zero automated recovery path. Fix needs two parts: (1) stop unconditionally re-throwing after a TTL grace window, fall through to FAILED/EXPIRED instead; (2) **build a BORICA-equivalent reconciliation cron** mirroring Stripe's, using `queryTransactionStatus`. M-7 (transient network error on stale-recovery) shares this exact root cause.
- **H-2 (BORICA cert expiry unchecked):** confirmed, zero expiry checking anywhere in the codebase for any provider. Test fixture is 3 years expired, demonstrating nobody tracks this. Fix: `new crypto.X509Certificate(certPem).validTo` check in config resolution, log on near-expiry.
- **H-3 (BORICA TRTYPE=22 reversal missing):** confirmed as a real gap, but report's "Stripe fallback" framing is wrong — it's a hard rejection to manual merchant-portal processing, same pattern as MyPOS/Cash/ePay (3 of 4 providers have zero automated refunds; only Stripe does). **This is a feature build** (new TRTYPE=22 signing + wiring into the refund dispatch), not a quick patch.
- **H-7 (MyPOS currency hardcoded EUR):** confirmed — the correct currency is already computed one line above and simply discarded. Same recurring pattern exists in BORICA per an existing test name (`#9`). One-line fix per provider, but check both.
- **H-8 (MyPOS missing Status = success):** confirmed, and it's a deliberate fail-open tradeoff documented in-code (comment `#M4`) — the team bet signature+reconciliation was sufficient. Confirmed this reasoning has a real gap (signature proves fields _present_ were signed, not that Status _should_ be present). Flip to fail-closed.
- **H-9 (refunds inflate per-method analytics):** confirmed for the **per-method** breakdown only — top-level collected/refunded split is correctly netted by the frontend already. Fix: add a `refundedByMethod` groupBy, subtract per-method (same gap exists in sibling `getPaymentsSummary`, not just the cited function).
- **H-10 (PENDING_PAYMENT orders inflate revenue):** confirmed. The team already fixed this exact distortion for `completionRate`'s denominator (tagged "Bug 2a") but never applied it to the revenue aggregates. One-line fix, same exclusion pattern, 2 call sites.
- **H-17 (stale cart price at checkout):** confirmed as a **UX** issue, not money-integrity — the backend is fully authoritative and always re-fetches current DB price; the customer can never be overcharged beyond the real price. Real gap: no warning shown if price changed between add-to-cart and submit. The POS flow already has the right mechanism (`expectedUnitPrice` + `PRICE_CHANGED` conflict) — reuse it for customer checkout, smaller change than it sounds.
- **H-21 (unbounded payment export):** confirmed, plus a bonus N+1-shaped eager-load risk in the same query. Add a hard row cap or enforce a max date-range.
- **H-22/H-23 (unbounded loyalty queries):** confirmed. H-22's fix is literally copy-paste — the correctly-paginated cron version of the same logic already exists in the same file.

### POS session concurrency

- **C-8 (order-creation TOCTOU):** confirmed real, but **the report cited the wrong branch** — the customer/QR order path it names (lines 452-478) has zero re-verification, which is correct, but the POS submission path (which is what "POS order creation" actually means in production — every real POS ticket goes through it) has a _subtler_ gap: it re-checks status inside the transaction but with a plain read, not a lock, so a race window still exists via a different mechanism than described.
