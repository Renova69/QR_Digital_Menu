# 🔴 CRITICAL FINDINGS

## Money & Payments

### C-1: Succeeded PaymentIntent after session PAID/CLOSED → money permanently unacknowledged

**File:** `apps/backend/src/payment/stripe-checkout.service.ts:1088-1108`
**Agent:** payment-provider-reviewer

`reconcileStripePendingPayment` retrieves succeeded intent but `claimSuccessfulPaymentForOpenSession` finds session already PAID/CLOSED. Returns `{ claimed: false, sessionPaid: false }`. Payment stays PENDING forever. Cron retries every 10min with same result. Customer charged, money invisible in all reporting (filtered by SUCCEEDED), no `payment:confirmed` emitted, no escalation path for manual reconciliation.

**Fix:** Flip payment to SUCCEEDED (or `RECONCILIATION_NEEDED`) when intent confirmed but session closed. Emit `payment:reconciliationRequired` so staff can refund.

### C-2: MyPOS card-terminal settlement has ZERO provider confirmation

**File:** `apps/backend/src/payment/session/payment-session.service.ts:499-505`
**Agent:** mypos-auditor

`closeSessionWithCard()` and `settlePartial()` with `SplitProvider.MYPOS` create SUCCEEDED payment with no communication with physical MyPOS terminal. No terminal connection check, no transaction reference, no response code, no receipt confirmation. POS operator presses "Paid by card" and system trusts unconditionally. Dishonest operator can mark any session paid. Honest operator whose terminal fails still has system marked paid.

**Fix:** Add terminal-reachable check before recording SUCCEEDED, or separate card-terminal path from online hosted checkout path entirely.

### C-3: BORICA/Epay/MyPOS private keys encrypted with JWT_SECRET fallback

**File:** `apps/backend/src/payment/secret-crypto.ts:8-11`
**Agent:** borica-auditor

Encryption key for `boricaPrivateKeyEncrypted`, `epaySecretEncrypted`, `myposPrivateKeyEncrypted` falls back through `JWT_SECRET` and `COOKIE_SECRET`. JWT signing secret reused for AES-256-GCM encryption of merchant private keys. Hardcoded `'dev-only-epay-secret-key'` in non-production. Compromised JWT secret decrypts ALL payment provider secrets.

**Fix:** Require dedicated `PAYMENT_SECRET_ENCRYPTION_KEY` env var. Never fall back to JWT_SECRET.

### C-4: Key derivation uses single unsalted SHA256

**File:** `apps/backend/src/payment/secret-crypto.ts:19`
**Agent:** borica-auditor

`crypto.createHash('sha256').update(source).digest()` — single unsalted SHA256 round for key derivation. Should use HKDF or PBKDF2 with per-provider salt.

### C-5: Partial payment tolerance 0.01 hardcoded in 5+ places

**Files:**

- `apps/backend/src/payment/core/payment-core.service.ts:997-1027` (main)
- `apps/backend/src/payment/core/payment-core.service.ts:578` (settlePartial)
- `apps/backend/src/payment/core/payment-core.service.ts:1229` (claimSuccessfulScopedCheckoutPayment)
- `apps/backend/src/payment/core/payment-core.service.ts:596` (createPendingPaymentAfterScopeGuardTx)

**Agent:** payment-provider-reviewer

If tolerances drift between paths, payment treated as "full" by one and "partial" by another. Extract to `PAYMENT_TOLERANCE = 0.01` constant.

## Data Integrity

### C-6: Analytics double `AT TIME ZONE` produces wrong hour/date for ALL non-UTC restaurants

**Files:** `apps/backend/src/dashboard/dashboard.service.ts:353,433,1058,1164`
**Agent:** analytics-accuracy

Pattern `((createdAt AT TIME ZONE 'UTC') AT TIME ZONE ${tz})` is incorrect. PostgreSQL semantics: `timestamptz AT TIME ZONE 'UTC'` → plain timestamp, then `AT TIME ZONE tz` treats that as already in `tz`. Order at 02:00 Sofia (stored 23:00Z UTC) → Step 1: `23:00:00` → Step 2: treats 23:00 as Sofia = 20:00 UTC → hour 20 extracted, NOT hour 2.

**Affected:** `getRevenueTrend`, `getPeakHours`, `getKitchenEfficiency`, `getCancelAnalytics`. All charts silently wrong for non-UTC restaurants.

**Fix:** Replace with `("createdAt" AT TIME ZONE ${tz})` — single conversion.

### C-7: Loyalty expiry reminder cron marks "sent" without sending

**File:** `apps/backend/src/loyalty/loyalty.service.ts:545`
**Agent:** future-break-risk

`runDailyExpiryReminders()` marks batches as notified in DB, but TODO block for actual email/push dispatch is empty. Every midnight the cron records "reminder sent" but customers never receive point-expiry warnings.

**Fix:** Implement actual email/push dispatch in TODO block.

### C-8: POS order creation TOCTOU race — no session re-verification inside transaction

**Files:** `apps/backend/src/orders/orders.service.ts:452-511,839-1095`
**Agent:** pos-session-auditor

Session lookup by token (`findFirst({ status: 'OPEN' })`) at lines 452-478 runs OUTSIDE main `$transaction`. By time order created inside transaction (line 1026), concurrent `closeSessionWithProvider`/`forceOpenSession` may have transitioned session to PAID/CLOSED_NO_PAYMENT. Transaction never re-locks or re-checks session status. Result: order attached to closed session, not billable, creates write-off.

**Fix:** Lock session with `SELECT ... FOR UPDATE` and verify `status = 'OPEN'` inside order-creation transaction.

### C-9: `closeSessionWithProvider` computes balance without pre-lock snapshot

**File:** `apps/backend/src/payment/session/payment-session.service.ts:522-583`
**Agent:** pos-session-auditor

Flow: reads session (OPEN), calls `abandonCheckoutOrThrowIfPending` outside transaction, enters transaction, locks session, computes balance. Between abandon and lock, concurrent order can be created. `computeSessionBalance` inside lock sees new order (INSERT not blocked by SELECT FOR UPDATE on session). Billed amount may include items ordered after waiter initiated close — over-collection.
